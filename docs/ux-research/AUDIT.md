## 1. Qué se verificó y qué no

La tesis de producto sigue siendo un **cuaderno académico que entiende una carrera argentina**: responder qué vence, qué se cursa, qué se habilita y dónde está el material, sin convertir al estudiante en administrador de un sistema. La evidencia actual proviene del código y la documentación del repositorio; una ruta existente **no demuestra** por sí sola que toda su operación de extremo a extremo haya sido probada.

## 2. Evaluación ejecutiva

La estructura básica tiene buenas decisiones: **Hoy** es una agenda y no un panel de métricas; el plan cita su fuente oficial y diferencia correlativas desconocidas; el calendario ofrece mes, semana y agenda; se puede cursar con carrera no catalogada; el primer inicio permite elegir carpeta local o Cloud; las notas locales se organizan por archivos y `[[enlaces]]`. El diseño es más maduro que la descripción de un POC minimalista, pero el producto ya mezcla dos contratos visuales distintos: **superficies editoriales de lectura** y **workspace de herramientas**. Deben compartir tokens y navegación sin comprimirse en el mismo ancho.

### Lo que no se concluye

- No se verificó tasa de éxito, abandono, tiempos de tarea, satisfacción o a11y dinámica. No hay observación de estudiantes usando el producto.
- El trabajo histórico `NOTEBOOK_REDESIGN.md` identifica defectos de septiembre. Algunos se corrigieron según el código actual (p. ej. el calendario **sí** tiene grilla mensual/semanal y el workspace es full-bleed), otros continúan plausibles (sidebar móvil abierta). No copiar sus conclusiones como si fueran nuevas mediciones.
- El producto tiene funciones implementadas en código; el estado **REAL** del inventario es «visible en fuente», no certificación end-to-end.

## 3. Flujos principales para diseñar y validar

| Flujo                  | Comportamiento REAL descrito en fuente                                                                                    | Pregunta de UX y criterio de aceptación                                                                                                                                 |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Primer uso local       | Selector inicial de carpeta; ruta sin cuenta local; luego onboarding a plan/progreso si corresponde                       | El usuario entiende **dónde se guardan** notas/datos; recibe una sola acción principal; llega a primera utilidad sin pedir usuario/contraseña local.                    |
| Primer uso Cloud       | Selector inicial habilita Cloud; login/signup; onboarding de cuatro elecciones, con salida manual                         | La ruta distingue cuenta de carpeta; si no existe plan puede continuar sin falsear correlativas; error de red no se confunde con «tu carrera no existe».                |
| Registrar avance       | Onboarding de plan catalogado lleva a `/plan/progress`; estados se guardan al cambiar; aprobar año admite deshacer        | El usuario identifica diferencia entre **regularizada**, **aprobada** y **equivalente**; cada cambio señala guardado; contradicciones se explican sin bloquear.         |
| Abrir cada día         | `/today` agrega atrasadas, hoy, próximas y sin fecha; lista materias cursando y final pendiente                           | Primer viewport indica qué hacer ahora sin contar elementos duplicados; no se empuja una tarjeta KPI por encima de obligaciones.                                        |
| Crear parcial/entrega  | `Ctrl/Cmd+K`, botón desktop y FAB móvil → modal con título/tipo/materia/fecha/hora                                        | De apertura a guardado con teclado en pocas acciones; materia preseleccionada desde detalle; error enfoca primer campo problemático; fechas sin hora son «todo el día». |
| Revisar plan y materia | Plan por año, barra de avance, fuentes y correlativas; detalle con fechas, notas locales, requisitos/desbloqueos, enlaces | Un plan **no publicado** expresa falta de datos; un bloqueo conocido explica cuál correlativa falta y qué habilita.                                                     |
| Preparar semana        | Calendario alterna Mes / Semana / Agenda y muestra obligaciones; eventos no se arrastran para cambiar fecha               | Se reconoce fecha, hora y materia en vista adecuada al ancho; interacción con evento no promete edición por drag.                                                       |
| Estudiar en notas      | Archivo local → explorer → editor CodeMirror → backlinks/Wikilinks → autoguardado y guard para salir                      | El editor ocupa lectura cómoda, el explorer no tapa móvil, se ve estado de persistencia, conflictos no silencian pérdida.                                               |

## 4. Benchmark conductual: qué aprender y qué evitar

| Referencia                                                                                                                                                   | Patrón publicado / estudiado                                                                                | Traducción **FUTURO** adaptada a Campus                                                                         | Límite                                                                          |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| [Things](https://culturedcode.com/things/features/)                                                                                                          | Jerarquía Hoy, Próximos, Algún día; quick entry y progreso sereno                                           | En **Hoy**, separar ahora, atrasadas y próximas; acciones contextuales mínimas, check de obligación de un toque | No inventar proyectos, áreas ni calendario automático de Things                 |
| [Craft](https://www.craft.do/blog/introducing-tasks) · [Calendar](https://craft-support.mintlify.app/en/plan-and-do/calendar)                                | Contenido es eje; tareas y notas diarias conectan planificación y escritura                                 | Tratar «Materia» como ancla de fechas, apuntes y material; cabecera editorial y controles calmados              | No imitar cards/decoración, sincronización de calendario ni arrastre de bloques |
| [Obsidian](https://obsidian.md/help/plugins/daily-notes) · [Bases](https://obsidian.md/help/bases) · [Backlinks](https://obsidian.md/help/plugins/backlinks) | Markdown local, enlaces entre notas, daily note y vistas filtradas                                          | Editor con lectura confortable, vínculos y búsqueda; explicar que las notas pertenecen a carpeta                | No proponer plugin ecosystem ni graph view como feature inicial                 |
| [AFFiNE](https://docs.affine.pro/) · `docs/research/AFFINE_STUDY.md`                                                                                         | Proporciones de workspace, paneles, modo documento; controles densos pero comprensibles                     | Explorer acoplado a editor, pane fluido a 1440, ausencia de tarjetas de fondo                                   | No copiar identidad, layout exacto ni funcionalidades Edgeless no existentes    |
| [Supernotes](https://supernotes.app/) · [Collections](https://help.supernotes.app/en/collections/1791371-switch-maintain-views)                              | Metadatos compactos y colecciones como forma de recorrer notas                                              | Filas académicas legibles, preview breve de recursos y contextos, chips discretos                               | No convertir apuntes largos en tarjetas atómicas por defecto                    |
| Guías internas                                                                                                                                               | `docs/research/WORKSPACE_REFERENCES.md`, `docs/research/NOTEBOOK_STUDY.md`, `docs/research/AFFINE_STUDY.md` | Aprovechar investigación previa, verificar fecha/versiones y licencias antes de adaptar código                  | Los juicios históricos no certifican la UI actual                               |

**Contexto argentino:** «regularizar una materia» y «aprobar el final» son hitos diferentes; «correlativa para cursar» y «correlativa para rendir» pueden ser reglas distintas; cuatrimestres, finales, parciales, inscripciones y equivalencias necesitan etiquetas propias. El plan puede ser institucionalmente incompleto. El lenguaje debe ser español rioplatense y fácil de identificar («Final pendiente», «Te habilita», «Fuente oficial consultada»), evitando metáforas de productividad corporativa. La arquitectura académica y la procedencia del dato son diferenciales de Campus frente a herramientas genéricas.

## 5. Sistema de diseño candidato para mockups

**Autoridad:** `WORKSPACE_DESIGN.md` para workspace; `design.md` para superficies editoriales; tokens efectivos en `src/styles/globals.css`. Los valores de referencia **no reemplazan** los tokens de producción: `paper`/`paper-elevated`/`paper-sunken`, `ink`/`ink-muted`/`ink-faint` (solo decorativo), `rule`/`rule-soft`, `accent`/`accent-soft`/`accent-ink`, `success/warning/danger` con texto.

| Rol         | Jerarquía visual y pauta                                                                                               | Restricción implementable                                                                                                                                                           |
| ----------- | ---------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Marco       | 220 px nav desktop existente; 4 tabs + Más en móvil; escritorio de notas y calendario full-bleed                       | `AcademicShell` ya maneja ambos contratos; `md` = 768, `lg` = 1024 en Tailwind, el documento workspace pide cambio efectivo a 1200: expresar propuesta y validar breakpoints reales |
| Tipografía  | Newsreader solo en título destacado y cuerpo del editor; Inter para controles, secciones y metadatos                   | Cargar fuentes existentes; texto del editor jamás subordinado visualmente al chrome                                                                                                 |
| Densidad    | Separaciones finas y filas de ≈40–48 px cuando la tarea es una lista; padding vertical generoso solo en hero o lectura | Escala de 4/8/12/16/24/36 px; evitar new tokens ad hoc                                                                                                                              |
| Superficies | Papel cálido, divisiones por reglas, overlays con borde y sombra muy sutil                                             | No gradientes, grain, stock ni drop shadows en cards de reposo                                                                                                                      |
| Interacción | Hover neutro 120–180 ms; seleccionado acento suave; foco visible 2 px y offset; overlays 180–240 ms                    | `prefers-reduced-motion`, teclado/tabulado, tamaños de toque, etiquetas ARIA                                                                                                        |
| Estados     | No usar solo color; siempre texto («Aprobada», «Bloqueada», «Correlativas no publicadas»)                              | Respetar fuentes, nulls del dominio y estado manual; nunca asumir disponibilidad                                                                                                    |

### Contratos responsive a revisar en imágenes

**390 × 844 (móvil):** top bar y navegación fija de cinco slots; contenido sin overflow horizontal; FAB solo donde el código lo permite; drawer/modales ajustados al teclado; área útil y safe area. En notas, explorar cómo cerrar explorador al abrir para no cubrir editor. Un solo pane.

**768 × 1024 (tablet):** desktop nav actual a partir de `md`, lo que consume ~220 px y deja ~548 px antes de padding. Es un punto de riesgo: comparar rail compacto **FUTURO** vs nav actual **REAL** sin atribuir el rail a la implementación. Calendar semana requiere test de legibilidad real.

**1440 × 900 (desktop):** superficies documentales centradas y medidas (`max-w-measure`); calendario y vault usan ancho restante y scroll interno; no introducir nuevo rail contextual por decoración. Workspace multi-pane debe preservar al menos una columna de lectura razonable.

**360 × 800 y 1280 × 800** quedan en la matriz de regresión de diseño original y deben evaluarse tras la aprobación.

## 6. Estados y microinteracciones imprescindibles

Para **cada pantalla** el diseño aprobado debe mostrar: normal con datos reales representativos, carga sin falsa información, vacío con una acción útil, error que permita reintentar, transición de guardado, diferencias de estado académico desconocido y foco de teclado. Un mockup estático puede presentar el estado principal y una banda de anotaciones de interacción; no añadir componentes de producción para simular animaciones.

Patrones concretos recomendados para validar: confirmación breve tras guardar entrega; fila permanece visible mientras cambia su estado en filtro; desfase de «Guardando… / Guardado» en notas; deshacer tras aprobar año; controles de modal muestran tecla Escape y retienen foco; un evento de calendario abre detalle y no se arrastra; la fecha sin hora comunica «todo el día»; explainer discreto de correlativas no publicadas; feedback de error de carpeta con acción para reintentar.

## 7. Roadmap de validación y puerta de aprobación

1. **P0 — Evidencia:** obtener runtime válido con datos de prueba no sensibles. Capturar y comprobar **390/768/1440** de startup, Hoy, Plan, Materia, Calendario, Notas y captura; registrar branch, fecha, URL, test case y estado, con DOM/a11y/overflow cuando proceda. Este punto no está completado.
2. **P0 — Propuesta visual:** generar primeras piezas en **ImageGen nativo**, una por composición, según [briefs](IMAGEGEN_BRIEFS.md), ancladas a una guía fija de tokens, con encabezado que diga **REAL ACTUAL** o **FUTURO PROPUESTO**. Iterar las imágenes con feedback de usuario.
3. **P0 — Aprobación:** el usuario elige opciones/variantes por pantalla y confirma jerarquía, densidad, navegaciones, colores, estados y responsive. Registrar resolución de discrepancias con `WORKSPACE_DESIGN.md`. **No comenzar implementación UI hasta esa aprobación**.
4. **P1 — Implementar por rebanadas:** empezar con mobile vault + estructura de shell y consistencia de estados; después Hoy/Plan/Materia; luego calendario/captura y refinamiento. Reutilizar React, TanStack Router y Tailwind v4, capacidades existentes y pruebas por comportamiento; ningún paquete nuevo por cosmética.
5. **P1 — Validar:** cada rebanada debe comparar captura antes/después en 360/390/768/1280/1440, foco/reduced motion, contraste, teclado, overflow, save/error/empty, dispositivo táctil. Usar scripts Playwright/axe existentes cuando runtime esté disponible; revisar discrepancias de mockup como decisiones explícitas.
