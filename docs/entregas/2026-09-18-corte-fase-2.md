## 1. Sobre el stack

La consigna menciona Flutter y Firebase. **Campus no usa ninguno de los dos, y es una decisión de la Fase 1, no un desvío.** El PRD define el producto como _aplicación web responsive, mobile-first pero capaz en desktop_, y el stack elegido para eso es:

| Capa                  | Tecnología                                                | Por qué                                                                                                                      |
| --------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| UI                    | React 19 + TypeScript estricto + Vite 7                   | Web responsive con un solo código para celular y notebook                                                                    |
| Ruteo / datos         | TanStack Router + TanStack Query                          | Rutas tipadas, caché y revalidación declarativas                                                                             |
| Estilos               | Tailwind v4 con design tokens propios                     | Design system tokenizado; modo claro y oscuro sin duplicar componentes                                                       |
| Base de datos (nube)  | **Supabase** (Postgres + Auth + RLS)                      | El equivalente directo a Firebase, pero relacional: correlatividades y planes de estudio son un grafo, no documentos sueltos |
| Base de datos (local) | **Vault**: una carpeta del estudiante con Markdown + JSON | El estudiante es dueño de sus datos aunque Campus desaparezca                                                                |
| Editor de notas       | CodeMirror 6                                              | Cuaderno con renglones, wikilinks y backlinks                                                                                |
| Calendario            | @dayflow/react (MIT)                                      | Motor de mes/semana/agenda; el contenido es nuestro                                                                          |

Firebase habría sido una mala herramienta para este dominio: un plan de estudios es una tabla de materias con aristas de prerrequisito entre ellas, y las consultas que importan ("qué se me habilita si apruebo esto") son joins. Postgres las resuelve; Firestore obliga a desnormalizar y a duplicar.

La app corre en **dos modos con la misma interfaz**: _Vault local_ (la carpeta del estudiante, sin cuenta ni red) y _Campus Cloud_ (Supabase, con cuenta). Toda pantalla habla con una única interfaz `CampusBackend`; ninguna sabe en qué modo está.

## 2. Estructura de datos (equivalente a "las colecciones de Firebase")

### 2.1 Postgres en Supabase — 12 tablas, todas con Row Level Security

Definidas en `supabase/migrations/`, con 42 sentencias de política RLS: cada estudiante ve solo lo suyo, y eso está garantizado en la base, no en la interfaz.

**Referencia académica** (datos públicos, de solo lectura para el estudiante):

| Tabla                 | Qué guarda                                                        |
| --------------------- | ----------------------------------------------------------------- |
| `institutions`        | Universidades (UTN, UNR…)                                         |
| `academic_units`      | Facultades / regionales (FRRo, FCEIA…)                            |
| `programs`            | Carreras                                                          |
| `curricula`           | Planes de estudio, con su fuente oficial y fecha                  |
| `subjects`            | Materias normalizadas                                             |
| `curriculum_subjects` | Una materia dentro de un plan: año, cuatrimestre, créditos        |
| `prerequisites`       | Aristas de correlatividad: qué hay que _cursar_ o _aprobar_ antes |

**Datos del estudiante** (privados por RLS):

| Tabla                    | Qué guarda                                                         |
| ------------------------ | ------------------------------------------------------------------ |
| `profiles`               | Perfil                                                             |
| `user_academic_contexts` | Qué institución / carrera / plan eligió                            |
| `user_subject_states`    | Estado por materia: cursando, regularizada, aprobada, equivalencia |
| `academic_items`         | Parciales, finales, entregas, clases, inscripciones — con fecha    |
| `resources`              | Material por materia                                               |

### 2.2 Vault local — la misma información, en una carpeta

```
Campus/
├── Daily/                     una nota por día
├── Materias/<materia>/        notas y material por materia
├── Exámenes/  Proyectos/  Recursos/  Inbox/
└── .campus/
    ├── vault.json             identidad y versión de formato
    ├── academic/
    │   ├── context.json       institución / carrera / plan elegidos
    │   ├── curriculum.json    el plan copiado, con su procedencia
    │   ├── subject-state.json cursando / aprobadas
    │   └── items.json         parciales, entregas, fechas
    └── trash/                 lo borrado, recuperable
```

Todo es Markdown y JSON legible: si Campus deja de existir, el estudiante se queda con carpetas que puede abrir con cualquier cosa.

> **Nota sobre las capturas.** La consola equivalente a Firebase es Supabase Studio, que corre localmente con `pnpm db:start` y necesita Docker. La máquina desde la que se arma esta entrega no tiene acceso a Docker, así que las capturas de Studio se toman desde otra máquina antes de subir. El esquema completo está en `supabase/migrations/` y es verificable directamente en el repositorio.

## 3. Qué funciona hoy

Ocho pantallas, todas conectadas a datos reales:

- **Hoy** — atrasadas, de hoy, próximas; materias cursando; progreso de carrera.
- **Plan** — el plan de estudios completo por año, con correlatividades resueltas: qué está disponible, qué está bloqueado y _por qué_ ("falta aprobar Física I").
- **Materias** — lista filtrable y **tablero Kanban**: arrastrar una materia de Disponibles a Cursando o Aprobadas persiste el estado. Con teclado también.
- **Materia** (detalle) — estado, correlativas, qué habilita.
- **Calendario** — mes, semana y agenda reales. Cada materia tiene su color; la intensidad dice si es parcial, entrega o clase. Modo claro y oscuro.
- **Vault** — cuaderno con renglones, explorador de carpetas, dos paneles, autosave, wikilinks `[[…]]`, backlinks, búsqueda y nota diaria.
- **Material**, **Ajustes** (tema claro/oscuro/sistema y color de acento).

Debajo de eso:

- **Correlatividades con procedencia.** El catálogo distingue "este plan no publica correlativas" de "no hay correlativas", y la interfaz lo dice en texto en vez de inventar un dato.
- **Design system tokenizado.** Cero colores hardcodeados en componentes; paleta de cinco colores semilla de la que se deriva todo por regla (OKLCH), incluido el modo oscuro y los colores por materia. El selector de color del estudiante solo puede producir colores dentro de esa armonía.
- **Seguridad del Vault.** Una única autoridad de filesystem del lado servidor, ligada a loopback, con token por proceso. Rutas resueltas con contención (sin `..`, sin symlinks fuera del Vault).
- **Verificación.** 412 tests automáticos (dominio, backends, runtime, servidor, diseño), typecheck estricto, lint, build de producción. Varios chequeos de layout corren contra un navegador real porque jsdom no hace layout.

Historia: 47 commits desde el 14 de agosto, ~14.400 líneas de TypeScript sin contar tests.

## 4. APIs y servicios que se usan finalmente

| Servicio                  | Uso                                                                             | Estado                                                                     |
| ------------------------- | ------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Supabase Auth             | Cuenta e identidad en modo Cloud                                                | Integrado                                                                  |
| Supabase Postgres + RLS   | Datos del estudiante y catálogo                                                 | Esquema completo, dos adaptadores (local y cloud) con tests de conformidad |
| Catálogo académico propio | Planes de UTN FRRo (ISI 2023) y UNR FCEIA, generados desde documentos oficiales | 40 materias, 186 correlativas cargadas                                     |
| Filesystem local (Node)   | Vault del estudiante, vía API loopback                                          | Integrado                                                                  |

No hay dependencia de APIs de terceros para el dominio académico: los planes se cargan desde documentos oficiales de cada universidad, con su fuente registrada. **Decisión explícita:** Campus nunca pide credenciales de la autogestión universitaria ni se conecta a los sistemas de la facultad.

## 5. Dónde estamos trabados / qué falta

Con honestidad, porque la consigna la pide:

1. **Capturas de Supabase Studio** pendientes por el problema de Docker descrito arriba. El esquema está en el repo.
2. **Cobertura de planes.** Hoy hay dos planes cargados (UTN FRRo ISI, UNR FCEIA LCC). Cargar más carreras es trabajo de datos, no de código, y cada plan requiere verificar el documento oficial.
3. **Crear y editar eventos desde el calendario.** Hoy se crean desde "Agregar" y se marcan como hechos desde el calendario; arrastrar un evento para moverlo de fecha aún no persiste, y por eso está deshabilitado en vez de fingir que funciona.
4. **Sincronización Vault ↔ Cloud.** Los dos modos funcionan por separado con la misma interfaz. Que un estudiante pase de uno a otro llevando sus datos es la pieza que sigue.
5. **Revisión adversarial.** El código pasa todos los chequeos determinísticos; la ronda de revisión con lentes de riesgo/confiabilidad/resiliencia está pendiente.

## 6. Coherencia con la Fase 1

La tesis del PRD: _un cuaderno académico personal que entiende la estructura real de una carrera universitaria_. Las siete preguntas que tenía que responder al entrar —qué tengo hoy, qué curso, qué se viene, cómo voy, qué depende de qué, dónde dejé el material, qué es relevante ahora— tienen hoy cada una su pantalla, con datos reales de un plan de estudios real.

Lo que se descartó explícitamente en la Fase 1 sigue descartado: no es un LMS, no es un Trello genérico, no es una demo de IA.
